# データベース設計

## 使用サービス

Amazon DynamoDB

## テーブル定義

**テーブル名:** `gtd-nodes`

| 属性 | 型 | 説明 |
|---|---|---|
| `PK` | String (パーティションキー) | `USER#{userId}` |
| `data` | String | ノードツリー全体のJSON文字列 |

## キー設計方針

将来の認証追加を見越して、最初から `USER#{userId}` のキー形式を採用する。

| フェーズ | PK の値 | 説明 |
|---|---|---|
| フェーズ1（認証なし） | `USER#default` | 固定の共通ユーザー |
| フェーズ2（Cognito認証後） | `USER#{Cognito UID}` | ユーザーごとに分離 |

フェーズ2への移行時はLambdaのコード変更のみで対応可能。DynamoDBのスキーマ変更は不要。

## サンプルアイテム

```json
{
  "PK": "USER#default",
  "data": "[{\"id\":\"550e8400-...\",\"title\":\"大グループA\",\"children\":[{\"id\":\"...\",\"title\":\"中グループA-1\",\"children\":[]}]}]"
}
```

## 設計上の判断

### なぜ1ユーザー1アイテム（JSON丸ごと保存）にするか

GTDのノードツリーはフロント側が常に全件を取得して操作するため、部分取得のメリットが薄い。  
1アイテム丸ごと読み書きすることでクエリをシンプルに保てる。

DynamoDBのアイテムサイズ上限は **400KB**。  
タスク数が数千件規模にならない限り問題にならないため、現フェーズはこの設計で進める。

### 代替案（フラット保存）

```
PK: "NODE#large-1",  SK: "META"
PK: "NODE#large-1",  SK: "CHILD#middle-1"
```

タスクが大量になった場合はこちらに移行を検討する。
